# 03：加入固定容量的每CPU事件记录

优先级：P1。开始条件：02的导出通道通过；建议3–6小时。

工作目录：`D:\x-kernel-dsh-bridge\submission\for github`。本文件是待执行任务，不是完成记录。

执行前先读 [总计划及统一交付规则](00_review_and_plan.md)。


## 本次只做

1. 执行内核修改前，阅读 `kernel/AGENTS.md` 及其诊断、代码规范要求。以同次bin/ELF/config建立诊断构建；保留默认关闭开关，区分正式候选与诊断候选。
2. 采用预分配固定容量的每CPU内存环，初始总预算128–256KiB。记录单调计数、CPU、事件类型、必要参数、提交序号与覆盖计数；处理读写一致性、同核中断嵌套和未完成记录。热路径不动态分配、不持续串口打印，不引入可能重入的全局锁。
3. 先只放在idle进入/退出、timer rearm及其目标、timer IRQ、IPI发送/处理、可运行任务入队/调度边界。记录足够的关联ID与关键状态；按实际代码缩减字段，不先做通用追踪平台。
4. 用02的宿主导出工具解码。验证绕回、覆盖、半写记录、未知schema；说明跨CPU顺序的时钟依据，不能仅按每CPU自增序号拼成全局时间线。

## 验收

正常短会话能导出并解码；CPU号/序号/长度有效，覆盖与丢弃可见，损坏记录可识别。至少展示一条真实timer或唤醒事件链。默认关闭不改变热路径行为；短开关对照记录功能/启动耗时和可见扰动，不能把诊断开销当性能收益。

未捕获停顿也可以完成“记录器实现”，但状态必须与“根因定位”分开；下一任务再取成功/失败对照。不得通过写入伪造事件来宣称已定位。
