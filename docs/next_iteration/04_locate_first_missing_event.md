# 04：捕获首个缺失事件并做单一修复

优先级：P1。开始条件：03可用；按假设分轮，每轮预算4–8小时，未定位则交接。

工作目录：`D:\x-kernel-dsh-bridge\submission\for github`。本文件是待执行任务，不是完成记录。

执行前先读 [总计划及统一交付规则](00_review_and_plan.md)。


## 必须先区分

全客机失去推进、Chromium无窗口、页面未提交、控制通道故障分别计类。旧run4四核同空闲PC、CPU/墙钟约0.215是线索；C07在100ms兜底tick后仍停，说明该补丁尚非充分修复。上一轮trace-01是DOM失败，不能替代全客机停顿事件轨迹。

## 本次只做

1. 固定一个诊断bin及匹配ELF，收集至少一轮正常轨迹与一轮真实停顿轨迹。QEMU串行运行；预先写明超时、串口/时钟停滞判据与采样窗口，不靠主观“等很久”。
2. 触发预定失败判据后，先记录宿主状态，再停止vCPU做一致性导出；保存停止前后的时间点。导出不依赖客机shell，禁止事后主动唤醒再称原始停顿已解除。
3. 从最近一次完整事件链向前后核对timer目标/使能、IRQ交付、IPI、runqueue、idle退出，定位可证伪的“应发生而没发生”边界。若环已覆盖关键窗口，记录证据不足，调整一次触发/容量后再试。
4. 仅对得到支持的边界做一项最小修复，附对应回归与相同条件的前后对照。不要同时缩短tick、改SMP、改浏览器参数和超时。

## 验收

`causal-chain.md` 引用可解码事件与同版本符号，说明替代解释如何排除；最小补丁有针对性验证。短对照不能宣称20/20或最终稳定。若只发现候选原因，写PARTIAL并列下一条能否证它的实验，停止重复大批启动。
