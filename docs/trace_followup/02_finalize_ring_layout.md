## 现有草案的具体问题

旧03的 `4×1024×32=131072` 已占满128KiB，不含头部和每CPU控制区；32字节entry列了seq/state/kind/arg0/arg1，却没有排序规则要求的timer counter。没有宿主读游标，也无法断言覆盖的是“尚未读取”记录。

## 本次只做

1. 给出可编译的数据结构和宿主schema，保留真实时间计数与频率/时间域说明。可采用40字节entry：seq/ticks/arg0/arg1各u64，kind/cpu各u16，flags或提交标识u32；这是候选布局，须按实际对齐和并发协议确认。
2. 预算以完整静态对象为准，含header、每CPU元数据、cache-line padding和记录。建议先采用不超过192KiB总预算，或相应减少entry数；不能继续把131072 entry字节称含头部总量。单次导出上限仍为1MiB。
3. 定义同核中断嵌套、槽位预留、发布顺序、绕回和半写识别；用epoch/seq匹配防止旧commit位被误读。最初仅承诺暂停后的冻结导出，暂不引入并发实时解码。
4. 无host消费游标时，计数写成覆盖/丢弃次数与保留范围，不称精确“未读丢失数”。跨CPU使用真实ticks和关联ID；相同或不确定时间不能强行全序。
